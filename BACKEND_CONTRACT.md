# MyCamCast backend contract

Use Supabase Auth sessions for all client requests. Anonymous access to application tables and media is denied. Account creation initializes `profiles`, `capture_preferences`, and `storage_accounts`. Configure mobile password-recovery deep links and Auth redirect URLs for the actual app before testing recovery. No secrets belong in the mobile bundle.

## Account entry and usernames

The existing mobile flow calls `auth.signUp({ email, password, options: { data: { username } } })`, then asks users to confirm their email and return to sign in with `auth.signInWithPassword`. Signup and email confirmation are enabled in `supabase/config.toml`; passwords must have at least eight characters. Resend uses `auth.resend({ type: 'signup', email })`. There is no custom password endpoint, username login, paid signup, or password-recovery callback in this release.

Site URL is environment-specific hosted configuration under Supabase panel → Authentication → URL Configuration. Shared `config.toml` deliberately omits it because publishing currently sends `env(...)` expressions literally. Development is set to the mobile sandbox's `/onboarding` page through the management proxy. Before publishing, check staging's Site URL against the mobile app's staging hostname and production's against its production hostname, both with `/onboarding`. The repository owns the exact redirect allowlist, password and email-confirmation settings. The frontend does not consume confirmation session fragments; returning and signing in is intentional. The mobile sandbox must be running when opening development links. No production service settings were changed directly.

Usernames are trimmed/lowercased and must match `[a-z][a-z0-9_]{2,23}`. The database unique constraint arbitrates concurrent signups. Reserved names: admin, administrator, camcast, camcaster, mycamcast, mycamcaster, support, help, system, moderator, official, root, supabase, draftbit. A failed username allocation rolls back the entire new account. Anonymous and authenticated clients may call `username_available(p_username)` before signup. It returns only a boolean; no email, owner ID, profile contents or account state are exposed. Invalid/reserved/missing names return false. The SECURITY DEFINER helper reads profiles with a fixed empty search path, performs no writes and does not reserve a name. The unique constraint still arbitrates races. The mobile client rechecks after a masked Auth database failure and describes a collision only when the check confirms unavailability. Confirmation responses must not be treated as evidence that an email was newly registered.

`profiles.username` is authoritative and immutable once claimed. User-editable Auth metadata cannot rename it or grant a paid plan. New accounts always receive the server's free 500,000,000-byte allowance and private capture defaults. Display name remains independently editable. Existing accounts retain sign-in access; only valid, nonreserved, unambiguous existing metadata is adopted. Others remain NULL and can call `claim_username(p_username)` once using their authenticated session. This RPC checks `auth.uid()`, locks only that profile, accepts identical retries, and rejects renames or another owner's name. A legacy claim screen would require a separate frontend change.

New incidents receive `creator_username` from their owner's authoritative profile, including inserts through `cast_control`. Clients cannot supply/change it. Existing footage remains NULL rather than acquiring guessed historical attribution; a later username claim never relabels earlier recordings. Username attribution does not publish a recording or verify a real-world identity. Existing UUID ownership and RLS still control access.

Email confirmation uses Supabase's existing template and delivery configuration. Development currently has no custom SMTP. Production email delivery needs a sender and credentials configured under Supabase panel → Authentication → custom SMTP, followed by a real inbox confirmation/resend test. These credentials must not be committed. Password recovery and paid checkout remain separate work.

Pending users can reopen the mobile sign-in page, enter the original email and choose Resend confirmation email without entering a password or repeating signup. Sign-in with an unconfirmed email explains this path. Successful requests use neutral wording rather than revealing whether an email is registered. Resend has a local cooldown in addition to Supabase's server limits. Confirmed users sign in with the email originally registered; a second signup with another email cannot claim their existing username. There is no additional mandatory onboarding-completion flag after Auth confirmation and initialized account rows.

Verification: `tests/auth_security.sql` checks signup atomicity, normalization, duplicates/reserved names, plan forgery, legacy claims, immutable attribution and owner/anonymous access. Run it against development through the SQL inspection tool; fixtures roll back. The capture and Active Cast SQL suites use valid account usernames as well.

## Capture and recovery

1. Persist a device-generated incident UUID locally; insert `incidents` with `id`, `device_started_at` (ISO UTC), `device_timezone`, and optional `is_test`, `title`, `notes`. Owner defaults to the signed-in user. On an ambiguous insert response, read the same ID instead of making a new incident.
2. Record independently playable video segments locally. Generate and persist each segment UUID, zero-based index, timestamps, byte size, MIME type, and optional lowercase SHA-256. Retain these files through network failures and app reopening.
3. Call `reserve_segment(p_incident_id, p_segment_id, p_segment_index, p_byte_size, p_content_type, p_started_at, p_ended_at, p_sha256?)`. Exact retries return the existing manifest. Conflicting IDs/indexes fail. Reservations consume allowance, including segments still waiting for upload. Maximum segment size: 20 MiB.
4. Upload each segment to `incident-media` at the returned `object_path` (`owner/incident/segment`, no extension), with its declared content type and **upsert: false**. This foundation uses standard per-segment uploads, not resumable uploads within a segment. Supported MIME types: `video/mp4`, `video/quicktime`, `video/webm`. A Storage trigger checks the server-generated size/type metadata and sets `incident_segments.server_received_at` atomically. Client-declared checksums are stored but not server-verified.
5. After success or an ambiguous response, read the manifest. Only a non-null `server_received_at` confirms receipt. A duplicate-object response is not sufficient. Keep local footage until confirmed. Poll manifests/status views; Realtime is not enabled in this release.
6. Call `close_capture(p_incident_id, p_ended_at, p_expected_segment_count, p_termination)` once the final segment count is known. Termination is `stopped` or `interrupted`; retry the same values safely. Closure is immutable. Missing segments may still be reserved/uploaded after closure. A resumed recording after closure uses a new incident. Unclosed incidents are unfinished, including those whose devices disconnected.
7. Read `incident_upload_status`: `capturing_or_unfinished`, `pending_upload`, `partially_uploaded`, `cloud_confirmed`, `interrupted_cloud_confirmed`, or `deletion_requested`. Cloud confirmation requires every expected unique segment. Interrupted captures remain explicitly marked. Device-only footage without a manifest is known only to the mobile app.
8. Read `storage_usage`: allowance, reserved bytes (includes confirmed), confirmed bytes, remaining bytes. Free allowance is **500,000,000 bytes**. Reservations serialize per account to prevent quota races. Allowance exhaustion rejects new reservations; keep recording locally where possible. Warn ahead of the limit. No auto-billing, automatic deletion, grace period, or retention deadline is implemented. Production limit/grace behavior needs product approval. `release_pending_segment(p_segment_id)` explicitly abandons an unconfirmed reservation without touching uploaded media.

`incident_events` accepts device reports of interruption, reconnection, upload failure, low storage, permission denial, and capture resumption. Stable event UUIDs make retries detectable. Server receipts/events cannot be written by clients. Record authorized location samples in `incident_locations` only after setting `capture_preferences.record_location`; include accuracy where available. Location-sharing consent is independent of location recording. The backend cannot establish whether OS permission was actually granted.

## Data access

All tables have RLS. An authenticated user can read only their own rows, with these catalog exceptions: available `storage_plans` and approved `partner_organizations`.

- `profiles`: owner updates display name; `capture_preferences`: owner manages capture/broadcast/location/notification defaults.
- `incidents`: owner inserts capture start fields and edits only title/notes. Original timestamps and server closure fields are immutable through direct client updates.
- `incident_segments`: owner reads; reservation/receipt/deletion RPCs manage writes. `incident_locations` and `incident_events`: owner reads and appends permitted device fields; no client mutation of existing samples/events.
- `trusted_contacts`: owner CRUD of name/email/phone/notify flag.
- `destination_connections`: owner selects platform/enabled; status defaults to `unavailable`. Only the server can set account labels or connection states. No OAuth credentials are stored here.
- `broadcast_sessions`: platform/state/provider-confirmed time/error; `notifications`: channel/recipient/state/queued/sent/delivered times/idempotency key. Owner reads; trusted server writes. No actual broadcasting or delivery occurs.
- `partner_interest`: authenticated applicant inserts the full interest form and reads own submissions. `partner_organizations` is server-managed. `incident_access_grants`: incident/recipient/partner/expiry/revocation/location scope; owner reads, server manages. These original grants still do not authorize recipient/media access. Active Cast uses separate hashed `cast_viewer_grants` described below.
- `storage_accounts`: owner reads, trusted server updates quota/plan. `storage_plans`: server-managed configurable allowance/optional prices; only the free plan is seeded, without invented prices.
- `purchases`: provider transaction/state/amount/currency; `entitlements`: export/storage scope/incident/expiry; `usage_events`: storage/processing/playback/distribution/notification/shared-access quantities. Owner reads; trusted server writes. These are provider integration foundations, not active billing or usage metering.

## Playback and deletion

`incident-media` is private. Owners may read confirmed originals and create short-lived signed playback URLs (recommend 60 seconds); recipients have no access yet. No overwrite policy exists. Playback is a sequence of independently playable segments; continuous live playback, thumbnails, transcoding, and exports require a later video pipeline. Browser/mobile container compatibility needs device testing.

Explicit deletion: call `request_incident_deletion(p_incident_id)`; fetch segment paths; remove objects using the Storage API; then call `complete_incident_deletion(p_incident_id)`. Requests revoke grant records and block new uploads. Owners retain media read access until object removal so the Storage deletion workflow can locate files. Existing signed URLs can last until expiry. Object removal releases associated quota; completion rejects remaining objects and cascades incident metadata. Retry any failed deletion steps. Never SQL-delete Storage objects: that does not remove underlying files. Full account deletion requires a later privileged workflow that removes all media before deleting the Auth user.

### Transport, auth and retry rules

Owner APIs: `POST {SUPABASE_URL}/rest/v1/rpc/cast_control` with `Authorization: Bearer <user access token>`, public API key in `apikey`, and JSON `{ "p_action": "…", "p_input": { … } }`. Alternatively `POST {SUPABASE_URL}/functions/v1/active-cast` with the same Auth session and JSON `{ "action": "…", "input": { … } }`. The facade verifies the session using Auth then forwards that user token; it never uses service-role privileges. The SQL invoker wrapper calls a private definer function with an empty search path and explicit `auth.uid()` owner checks. Anonymous and cross-account access are denied. Exposed tables are owner SELECT only; all application writes use RPCs. X is now a valid `destination_connections.platform`; account labels/state remain server-only.

All mutating actions require a persisted client UUID `request_id`. Retry **identical action/input/UUID** after timeout, network failure or ambiguous response. The ledger returns the original result even if preferences or control state changed later. Reusing a UUID with different data raises `idempotency_conflict`. A new end UUID returns the existing stop time without duplicate outbox entries. Read `status` for current state. Do not interpret a retried start response as current broadcasting/capture status. Never wait for this HTTP call before starting native capture or persisting its local incident UUID.

Dates are ISO UTC strings; IDs are UUIDs except preset IDs. Cursor values are decimal strings. Inputs and outputs are also defined in `contracts/active-cast.ts`; these are handoff types, not generated Supabase database types. Action inputs below omit `request_id` on read operations. Do not put tokens, credentials or viewer links in titles, notes, events, analytics or logs.

Direct RPC semantics are authoritative. A preset revision conflict is a successful SQL result `{error:"revision_conflict",current:Library}`; the Edge facade maps it to HTTP 409. Refetch/merge explicitly and use a new request UUID; never retry stale data as an unconditional overwrite.

### Preset library and migration from device storage

`Library = {owner_id,revision,presets:Preset[],favorite_ids:string[],updated_at}`. Maximum 100 presets. Each preset contains `id,name,description,artwork,builtin,socialPlatforms,liveView,sendLocation,recipients:[{name,phone}]`, with optional `legacy_name`. `favorite_ids` is the authoritative ordered quick-connect row; local `favorite` booleans are not stored. Library-level compare-and-swap and an owner row lock serialize concurrent devices and enforce at most four unique, existing favorites transactionally.

Core IDs, names, descriptions and artwork match mobile's current `preset-model.ts` exactly: `traffic-stop`, `police-encounter`, `stranger-encounter`, `altercation`. All four are required and cannot be deleted. Ordinary saves reject core identity edits; explicit legacy import restores canonical metadata. New custom IDs must be UUIDs. Custom names are trimmed, 1–12 Unicode characters; render the first six and remaining six as two text lines, using `artwork:"text"`. Descriptions have at most 240 characters. Legacy import permits names up to 64 and sets `legacy_name`; unchanged legacy name/description may survive other preference edits, but editing either requires shortening the name. Server does not infer sharing consent from preset settings. Platform arrays are deduplicated to facebook/tiktok/youtube/x/twitch. Each preset has up to 20 distinct normalized E.164 recipients, `+` plus 7–15 digits, first digit nonzero; whitespace/parentheses/dashes/dots are stripped. Recipient names may be empty, maximum 80 characters. Number formatting is not verification of ownership or consent.

Read the server library first. If revision is zero, explicitly offer importing the preserved device list, derive favorite order from device order, and send `presets_import` with a persisted request UUID. Missing sharing flags/platforms/recipients default off/empty. Revision >0 means the server has data: present conflicts to the user, preserve the local copy, and explicitly merge via `presets_save`; never silently replace the server. Successful import replay is idempotent. Saving preferences creates no incident, grant, notification or broadcast.

### Start/end and snapshots

Example owner RPC body (substitute locally persisted UUIDs):

```json
{
  "p_action":"start",
  "p_input":{
    "request_id":"00000000-0000-4000-8000-000000000001",
    "incident_id":"00000000-0000-4000-8000-000000000002",
    "preset_id":"traffic-stop","preset_revision":1,
    "device_started_at":"2026-11-03T12:00:00Z","device_timezone":"UTC",
    "consent":{"video":false,"location":false,"sms":false,"platforms":[]}
  }
}
```

`start` atomically creates an incident before any completed segment, or adopts the incident already registered by native capture. Start time/timezone/test flag must match. `active_casts` stores an immutable normalized preset snapshot (including recipients and destination preferences), and explicit session consent. Requested session sharing scopes/destinations must be a subset of preset choices. Changing the library cannot change this session. Repeated registration uses the original request ID. Owner rate limit is 60 registrations/hour. Native recording may proceed offline and register later; network control success is never recording-start confirmation.

`end` requests sharing stop and immediately revokes this release's recipient grants. It does not call `close_capture`, change expected segment count, remove originals, release quota, or cancel queued uploads. After native capture determines its final count, call `close_capture` exactly as in the capture contract. Late reservations/uploads remain allowed inside that count. Never use an empty/guessed final count. Start after immutable closure requires a new incident ID.

One `cast_jobs` SMS intent exists per `(incident_id,kind:'sms',target:E.164)`; its payload contains both requested booleans when both scopes are requested. Consent `sms:false` never creates an SMS intent. There are no link URLs, sent notifications or provider requests until a real sender/viewer integration exists. The existing `notifications` and `broadcast_sessions` table shapes and owner reads remain compatible with mobile `active-events.ts`. Broadcast preferences produce `state:'unavailable'` with `<platform>_oauth_eligibility_and_ingest_not_configured`, never `live`. End intents are separate from start/SMS intents. A previously confirmed live broadcast stays live until provider confirmation of end; an unconfirmed end surfaces `provider_end_unconfirmed_may_still_be_live`, not a fabricated end time. `provider_end_confirmed:false` is deliberately conservative even when no destination was requested.

### Recipient capabilities, location, presence and messages

Create 32 cryptographically random bytes in the issuing trusted client/server; encode as 64 lowercase hex characters. Persist the raw token securely on the issuing device before sending the request so a network retry does not mint a new capability. Compute SHA-256 over that **hex string's UTF-8 bytes**, send only the 64-character hash in owner `grant`, and keep the raw token only in the recipient link fragment `#token=…`. Stable `grant_id` and `request_id` make issuing idempotent. A grant is scoped to one incident and a recipient number from its frozen snapshot, lasts at most 24 hours, and cannot exceed session video/location consent. A bearer link proves possession, not a verified person; do not label the recipient identity verified. `cast_tokens` stores hashes in a non-exposed schema. Neither owners nor anonymous clients can select it. Owners can revoke/block immediately. End or incident deletion denies further access. Already delivered data cannot be recalled.

Recipient endpoint: `POST {SUPABASE_URL}/functions/v1/cast-viewer`, `Content-Type: application/json`, JSON `{ "token":"<64 hex characters>", "action":"heartbeat|location|message", "input":{} }`. No Supabase user session or API key is required. JWT verification is disabled only at this gateway: it hashes the capability and calls service-only `cast_viewer(p_token_hash,p_action,p_input)`. Every operation revalidates grant expiry, revocation, blocking, incident deletion and stop. No owner storage URLs or original media are returned. Tokens in query parameters are rejected. The function never logs bodies/URLs/tokens or database error details. Responses are `Cache-Control:no-store`; browser origins must match comma-separated `CAST_VIEWER_ORIGINS` Secret. Empty allowlist denies cross-origin browsers, while non-browser requests still need a valid capability. `CAST_OWNER_ORIGINS` controls browser access to the owner facade; native and direct RPC clients remain usable. Invalid/revoked/expired/out-of-scope access returns 403; message throttling 429, conflicting retries 409, malformed input 400, oversized body 413, non-JSON 415. Bodies are stream-limited to 8192 bytes. Successful access is audited by grant/action/time, coalesced over ten seconds, without tokens or raw IPs. Configure gateway abuse controls/observability before public launch.

`heartbeat` returns `{expires_at,heartbeat_seconds:15,identity_verified:false,video_state,location_authorized}`. Heartbeat every 15 seconds. Presence is one record per grant, coalesced to ten seconds, and expires after 45 seconds. Owner `status.camcast_viewer_count` counts distinct currently authorized grants with fresh presence, not human identities, tabs or confirmed video playback. Location-only recipients can count; label it as authorized CamCast viewer sessions. Revoked/expired/blocked/deletion-requested grants do not count. External platform counts are separate and currently unknown (`{}`), never substituted or fabricated as zero.

`location` owner input requires `capture_preferences.record_location:true` for collection and a separate session `consent.location:true` plus per-sample `share_with_recipients:true` for sharing. Legacy `incident_locations` and owner-only Active Cast samples never become shared automatically. The backend cannot prove OS permission; mobile must collect only after OS authorization and explicit collection/sharing choices. Accepts latitude ±90, longitude ±180, finite nonnegative accuracy and original device timestamp (not over 30 seconds in the future or more than 24 hours before capture). Sample ID and request UUID must remain stable across retries. Offline old fixes stay old. Recipient action `location` returns `{state:"no_shared_fix"}` or `{state:"approximate_fix",latitude,longitude,accuracy_m,device_recorded_at,received_at,age_seconds,stale}`; the most recent **device timestamp** wins even when upload order differs. Stale means older than 60 seconds. Always show recorded time and accuracy, never “current location” for a stale fix.

Recipient `message` input is `{message_id:<stable UUID>,body:<1–500 trimmed characters>}`. Retries with the same ID/body/grant return the same moderation status. Different data conflicts. At most five new messages/minute/grant and 10,000/incident. `cast_messages` is an owner-only moderation queue. Default is `pending`; nothing enters the feed before owner approval. Verified identity is always null in this release; display “Guest.” The moderation transition is pending→approved/rejected, approved→removed, with exact retries allowed. Approval checks current grant authorization. Blocking revokes future access; owner may also remove historical messages. No external moderation provider or automatic content safety claim exists.

Poll owner `feed` while Active Cast is open every 5–7 seconds, retaining the last cursor; limit is clamped to 1–100. It returns ordered approval/removal events, stable `message_id`, `kind`, nullable `body`, `sender_label`, `verified_user_id`, `occurred_at` and string `cursor`. `next_cursor` advances only to the final returned event. Continue immediately while it differs from `head_cursor`, then resume bounded polling. Start with `after:"0"` for full durable post-incident history. Approval assigns the sequence under the incident lock, so late moderation of an older message never falls behind an already consumed cursor. Persist the cursor with the reducer state; deduplicate event cursors, upsert by message UUID and apply removal tombstones. A removed message's original body is redacted on replay. Raw pending/rejected messages are not rotating-hub deliveries. No Realtime publication, owner chat-input requirement or audio auto-read is introduced.

### Browser viewer and outstanding service prerequisites
